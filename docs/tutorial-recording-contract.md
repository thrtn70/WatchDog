# Tutorial workspace and pause-aware managed contract

This is a managed source design for R2.2/R3.1 with a tutorial workspace connected to the existing controller through a per-workspace command adapter. Production construction still denies tutorial Start; native recording qualification, preview, countdown, pause, resume and manual split remain pending. `TutorialRecordingPolicy`, `TutorialWorkspaceProjection` and `TutorialTimelineContract` neither enumerate devices nor acquire capture resources. The existing `CaptureLifecycleCoordinator` remains the only resource owner. Gaming and tutorials retain equal priority; the intended workspace works locally without accounts, telemetry or automatic upload.

## Existing source boundaries

| Source | Existing contract | Required behavior |
|---|---|---|
| Window | `WindowCaptureTarget`, manual manager route | Retain exact PID/HWND. Native admission must revalidate the window and required selector metadata. A title is descriptive, never permission to choose a similarly named replacement. |
| Display | `DisplayCaptureTarget`, backend and configured route | Retain stable display ID; a legacy monitor ordinal alone is insufficient. Whole selected display is the explicit boundary. The workspace confirms an exact currently offered display target; production Tutorial Start remains denied. |
| Region | `RegionCaptureTarget`, manual manager route | Retain physical rectangle and frozen owning-display bounds. Reject invalid, overflowing, cross-display or moved geometry; never widen to the display. |
| Webcam | `WebcamCaptureSelection`, independent recorder | Require a fresh explicit choice/consent for this tutorial plan. A saved preference alone adds no camera to the plan. Use one exact device and retain independent camera media. |
| Audio | `AudioMixConfig`, `AudioTrackPlan`, admitted device manifest | Show startup system/microphone enablement and combined track 1 or stable separate tracks 1/2. This plan does not select, validate or reconfigure audio devices. The existing owner reports actual admissions. |

`CaptureRequest` freezes the manual source, optional camera and session output policy. A tutorial plan explicitly chooses `SessionRecording`, even when saved gaming defaults use replay; it does not modify saved defaults. Other recording settings, including automatic segmentation and duration limits, are inherited and sanitized. This choice must be shown before any future Start route dispatches it. Separate audio requires MP4/MKV. Unsupported encoders remain actionable; software fallback is explicit. Engine admission and recording success remain separate from planning readiness.

The current backend starts its capture stopwatch before starting screen output, while the session recorder starts its own stopwatch later. Camera offsets use the backend clock; screen segments use recorder elapsed time. Existing `SessionMediaSegment` offsets therefore remain estimates from different origins. Neither the current enum label `BackendStopwatchEstimate` nor historical synthetic receipts establish current screen/camera synchronization. This slice does not rewrite persisted offsets. Model/presentation correlation conservatively includes the full frozen target record, including descriptive metadata; a future resolver must bind that resolved target before dispatch.

3. Show session recording mode, encoder/output scope, canonical save destination, segmentation and duration limit. The destination is `Storage.SavePath`; backend persistence and settings own its application. This policy adds no filesystem access or alternate destination.
4. Keep Start unavailable until a separately reviewed production route binds the plan and startup audio metadata to the actual startup baseline. Preview/countdown remain unavailable with explanations. No delayed admission, hidden preview capture or second lifecycle owner is implied.
5. After future dispatch, project owned lifecycle snapshots by exact frozen request and physical boundary. Show Starting, Recording, Saving, Stopping, closed admission and retained cleanup truthfully. Stop goes through the existing owner with manual initiation and awaits its typed result. Pause/Resume/Split stay disabled with a visible reason; no paused indicator or “resume” implemented as a hidden restart.
6. Source loss stops the exact context and explains the failure. Idle/null cannot prove whose manual reservation is retained: show ownership unknown and disable this projection's Stop control until an exact correlated context is available. A future explicit recovery flow needs an owned coordinator outcome before offering reservation release; the existing coordinator remains the authority for manual Stop. An unrelated automatic/manual capture must never be displayed as this tutorial recording. Failed cleanup keeps its context and a Stop retry rather than optimistic idle UI.

The compiled projection provides status and boundary/audio text plus immutable unavailable-control reasons. A separate tutorial workspace is reachable from the main window. It uses an explicit window-list opening/refresh, copies one current offered record into a plan, checks PID/HWND ownership again at confirmation, and shows exact PID/HWND/class metadata, startup audio and planned output. It has accessible names, keyboard confirmation, focus restoration and a live status announcement in source; WPF usability has not been run. The workspace projects backend failures as a generic live warning because raw exception details may contain local paths or device identities. This workspace does not reuse the manual capture picker, whose selection immediately dispatches capture. Display selection now uses an explicit Refresh, immutable offered options and the existing engine stable-identity resolver. The entire selected display is the boundary. An advanced numeric region selector now confirms a physical rectangle within one exact display using the existing resolver; visual drag selection and preview remain unavailable. The optional camera selector is default-off, reads only the existing physical-device metadata catalog after an explicit Refresh, shows a local option number beside the descriptive label while retaining the exact opaque ID internally, and requires a fresh exact-record confirmation for this plan. A saved camera preference never grants consent; refresh, disappearance, source change or cancellation revokes it. Failed exact-window revalidation also revokes the entire plan and camera consent. The requested camera format is frozen as metadata but native support and capture remain unverified. The workspace now uses `TutorialWorkspaceCapture` over the manager-owned `TutorialCaptureController`. Connected Start revalidates the exact window, full display target or frozen region immediately before dispatch; unsupported target types fail closed. Submitted revision/plan ownership is separate from the editable draft: editing or refreshing during pending Start revokes intent, and late acquired resources are reconciled through the existing owner. ## Exact-display metadata selection

`DisplayCaptureCatalog` defers enumeration until an explicit caller request and accepts injected screen metadata, device-name resolution and stable-ID resolution for managed tests. Tutorial options retain the original engine `DisplayCaptureTarget`, including its name and monitor index. The Windows screen ordinal and the Settings label are presentation metadata and never reconstruct capture identity. Stable-ID re-resolution must equal the complete confirmed record; missing identity, ambiguity, changed name/index or resolver failure rejects confirmation/Start without display-index or desktop fallback.

The tutorial consumer rejects a malformed or ambiguous snapshot as a whole, clears previous options/confirmation and reports a fixed message. It rejects blank/duplicate stable IDs, case-insensitive duplicate device names, invalid dimensions and unavailable stable-ID resolution. Highlighting an offered option is only a candidate; explicit confirmation must refer to the current offered instance. Refreshes, source-type changes, selection replacements and failures revoke pending intent and camera consent. A copied or old option cannot silently substitute for a newly offered record.

Settings uses the same catalog's separate legacy monitor projection. Its row order, screen index, labels, unresolved empty IDs and saved stable-ID/index selection rules remain unchanged. The tutorial's stricter admission rules do not silently filter or change saved Settings choices.

Display Refresh is explicit and does not run when the workspace loads. It reads metadata only when invoked in a future interactive session; this implementation's tests use injected data and do not enumerate the machine's screens. The optional camera confirmation flow remains limited to confirmed windows; selecting a display turns camera consent off. Production Start, visual drag selection, preview/countdown and pause/resume/split remain unavailable. The existing manager/backend repeat exact display identity checks; managed selector evidence does not prove captured pixels, native identity stability or native cleanup.

## Explicit physical-region confirmation

The advanced region selector uses an explicitly selected current display and string drafts for global physical-pixel X, Y, width and height. X/Y may be negative on multi-monitor desktops; width/height must be positive. Text changes reach the view model immediately and revoke older confirmation, including incomplete or invalid edits. No missing coordinate defaults to zero, and WPF numeric conversion cannot retain a hidden older value.

`TutorialRegionSelection` parses invariant integer text with overflow-safe arithmetic. Only explicit Confirm resolves the region. It requires the exact current display owner, the exact requested rectangle, a returned target with the same ordinal owner ID and rectangle, valid frozen owner containment, and current region availability. Both owner and region overflow are rejected. Null, mismatched, cross-display or unavailable results and resolver failures cannot broaden the source. The original immutable returned `RegionCaptureTarget` is retained; Start revalidates that target and its selected owner without resolving or reconstructing it.

Owner/offer and edit revisions bind confirmation to the draft that actually requested resolution. A callback, refresh, coordinate edit, source change, close or disposal that invalidates the draft prevents stale publication. A newer nested confirmation is not discarded by an older callback result. Source fields and region status follow the submitted plan while a pending Start or retained cleanup owns it; editing remains blocked once cleanup is retained. Region selection clears camera consent, and camera configuration remains window-only.

View-model presentation notifications are deferred while the command adapter binds a confirmation revision. A presentation observer can then edit, confirm a replacement, close or dispose without leaving the previous confirmation authoritative. This covers view-model observers; atomic confirmation against subscribers attached directly to the controller or adapter remains a separate contract to review.

This is numeric entry, not a visual region picker. The display catalog's dimensions provide no origin or DPI provenance. No origin is inferred from them, and there is no drag/DIP conversion, preview, coordinate probing or native capture in this slice. Native geometry, actual pixels and real cleanup require separate qualification; the production Start gate is unchanged.

## Modeled pause-excluded timeline

`TutorialTimelineContract.Create` consumes an ordered packet of explicit Recording/Paused intervals. Each interval names session ID, request ID, positive generation, exact actual target and a caller-supplied nonempty epoch ID. Offsets are nonnegative `TimeSpan` values from epoch zero. Intervals must have positive duration and be contiguous: gaps, overlaps, regressions, foreign identities and undefined kinds reject the whole packet. An empty packet is an empty model; it implies no native start/end. No clock is read and no boundary is synthesized.

For a modeled recording `[0,2)`, pause `[2,7)` and recording `[7,10)`, playback contains two retained intervals beginning at 0 and 2 seconds, with total duration 5 seconds. Camera, screen, audio and later cursor/annotation layers would all need verified alignment to these same boundaries. A trailing paused interval contributes capture elapsed time and zero playback time. The plan copies interval collections; caller edits cannot change it. `NativePauseProven` and `NativeAlignmentProven` are fixed false. The model cannot be fed directly into current media/export paths as qualified timing.

## Missing native contracts before enablement

| Contract | Required evidence before a production control can change state |
|---|---|
| Serialized command/ack | Pause/resume/split must run under the existing lifecycle owner, carry operation/session/request/generation/source/epoch identity and reject stale acknowledgments. Cancellation before admission may reject; once resources change, reconcile to the actual owned state. |
| Output capability | Explicit support for screen output, independent camera, every audio track and future cursor collection. All required participants must support the same operation. The current recorder/backend interfaces expose Start/Stop/Save, not these commands. |
| Atomic pause/resume outcome | Report native success and exact effective media boundaries. Partial success must produce a truthful failure and ordered stop/finalization of all retained outputs; it must not report Paused while one stream continues. Never change capture scope during recovery. |
| Liveness during intentional suspension | A separately admitted liveness owner must distinguish an acknowledged pause from a stalled output, preserve device/source-loss checks, and revalidate progress expectations on resume. No heartbeat suppression or production liveness admission is enabled by this model. |
| Monotonic epoch/PTS | Establish one epoch across all participants, mapping actual muxed timestamps to pause-excluded playback and retaining provenance. Stopwatch estimates alone cannot qualify sample/frame alignment. Delayed camera startup, rotation and trailing pause must be represented explicitly. |
| Split/finalization | Correlate finalized segments and unique file paths, preserve originals, drain ingestion before completion and prevent late segment/timer callbacks from restarting after pause/stop. Automatic file segmentation is a separate existing feature. |
| Preview/selection | Define consent, exact boundary, lifetime, admitted devices and resource release for preview. Revalidate display geometry/window identity at Start; metadata selection does not prove captured pixels. |
| Metadata/recovery | Version durable timeline/epoch/boundary provenance without changing historical estimates into native timestamps. Preserve failed/partial originals and actionable recovery. No second persistence or cleanup owner. |

The application coordinator continues to return typed `Unsupported` for Pause/Resume/Split without state mutation or backend calls. A pure state or interval model does not satisfy the above contracts. New UI availability must remain gated until those source contracts and their separately authorized qualification pass.
